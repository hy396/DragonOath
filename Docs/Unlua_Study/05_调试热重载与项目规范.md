# 05 调试、热重载与项目规范

Lua 的优势是迭代快，代价是大量错误要到运行时才暴露。把日志、错误定位和职责边界当作第一等工作，才能不让脚本层变成不可维护的黑盒。

## 1. 最实用的调试方式

```lua
print("[UnLuaTutorial] value:", value)

assert(value ~= nil, "value must be initialized before use")
```

- `print`：先用统一前缀，便于在 UE Output Log 中筛选。
- `assert`：用于开发期的不可违反前置条件。失败后会中断当前 Lua 调用，不应把它作为正常业务分支。
- 报错通常会含 Lua 文件名、行号和调用栈。先修复**第一个**错误，后续错误经常是连锁反应。

推荐日志格式：`[UnLua][功能名] 内容`，例如 `[UnLua][Dialogue] Node entered: Intro_01`。

## 2. 热重载的正确预期

修改 Lua 文件不需要重新编译 C++，但“文件修改立即对所有实例生效”并不是无条件保证。`require` 会缓存模块；已经创建的 Lua 对象也可能保留旧状态。不同 UnLua 版本和运行模式对重载时机有差异。

可靠的学习流程：

1. 修改 `.lua` 并保存。
2. 在当前插件版本的 UnLua 编辑器命令/控制台入口执行热重载，或停止 PIE 后重新开始。
3. 用 `ReceiveBeginPlay` 日志确认新代码实际被加载。
4. 涉及模块结构、UE 回调绑定或对象状态时，优先重启 PIE；无法确认时再重启编辑器。

不要为了“实时生效”在正式流程里手写全局 `package.loaded` 清理。那会让旧实例、闭包和 UE 对象引用的状态关系难以预测。

## 3. DragonOath Lua 规范

| 规则 | 原因 |
| --- | --- |
| 每个文件只导出一个模块 table | `require` 依赖清楚，便于重载与审查 |
| 默认使用 `local` | 避免全局命名冲突 |
| 变量和函数用 `snake_case` | 与 C++ 的 PascalCase、UE 属性名清楚区分 |
| Lua 调用 UE 属性仍使用其原始暴露名称 | UE 反射按资产/C++ 定义映射，不能自行改名 |
| 所有日志带 `[UnLua]` 与功能名 | 日志可检索 |
| 不把 Actor、Widget、ASC 长期塞进全局 table | 防止生命周期和引用问题 |
| 网络结果只读/展示，核心裁决在 C++/GAS | 保持服务器权威 |

## 4. C++ 暴露 API 的推荐形状

当 Lua 确实需要调用项目能力时，C++ 应暴露一个小而明确的 `BlueprintCallable` / `BlueprintPure` 接口。Lua 调用接口，不直接依赖内部成员或私有实现。

```cpp
// C++：仅展示本地提示，不改变权威游戏状态。
UFUNCTION(BlueprintCallable, Category = "DragonOath|Tutorial")
void ShowLocalTutorialPrompt(const FText& Message);
```

Lua 侧只调用这个已批准的表面：

```lua
self:ShowLocalTutorialPrompt("Press the interaction key")
```

这条边界使 Lua 可以快速调整内容，C++/GAS 仍能保持稳定、可测试的核心逻辑。

## 5. 何时停止用 Lua

出现以下任一情况，应把逻辑下沉到 C++、GAS 或 DataAsset：

- 逻辑决定了伤害、命中、资源消耗、冷却、掉落或经验。
- 行为需要客户端预测、可靠复制或反作弊。
- 需要高频 Tick、大量对象遍历或有严格性能预算。
- 逻辑数据结构已复杂到需要静态类型、单元测试和 IDE 重构保障。

下一章的 POC 保持在“本地提示编排”，用它验证完整工作流而不触碰这些边界。
